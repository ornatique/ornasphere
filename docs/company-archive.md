# Company Profile Archive / Restore

The last Company Profile section is available to that workspace's company administrator. New archives from a main company include that company and all descendant branches, including inactive branches. A branch administrator can archive only their own branch, not the parent or siblings. No real archive, deletion or restore is executed by installing this code.

## Workflow and scope

### Non-destructive copy-only download

Company Profile also offers **Download copy-only backup**, requiring the own-company administrator's current password and a new confirmed backup password. It reads the main company and current descendant branches in a read-only repeatable snapshot without creating/updating archive state, counters, business rows, users, tokens, or queues. Invalid links (including cross-company `sale_payments.sale_id`) are preserved verbatim and summarized in encrypted `dependency_warnings`; foreign-company parent rows are never pulled into the copy. Account snapshots use the existing login/session-field sanitization.

These separately marked **format-v6 / purpose=copy_only** encrypted ZIPs include scoped records, available local attachments, cloud paths and signed lists of missing attachments. Missing documents are listed instead of blocking a non-destructive copy; missing file content cannot be recovered from this ZIP. Cloud objects are never read, changed or deleted. This mode has no remove step and does not resume an existing paused archive. Creating/downloading a copy is independent of the original archive lifecycle.

The standard archive verifier/remover/restorer rejects copy-only ZIPs before any business import or removal. Recovery from a copy needs a separate reviewed procedure to resolve its references; it is not an automatically restorable archive. Existing formats v1–v5 and their ownership/removal checks remain unchanged. The web route is `POST /company/{slug}/profile/archive/copy`; this upgrade has no migration.

1. Re-enter the account password, choose a separate archive password (minimum 12 characters) and confirm it. The Profile lists the included workspaces before confirmation. Attachment availability is checked before pausing, so an incomplete file copy or unavailable image storage does not freeze the workspaces. The entire selected company/branch group then pauses atomically while existing admitted requests finish. If a branch still has requests running, retry preparation after they finish or cancel the group.
2. Create one AES-256 encrypted ZIP containing business records, declared attachments and informational snapshots of retained account/settings records for all included workspaces. No SQL scripts are generated or executed. An HMAC-authenticated manifest and every entry's SHA-256/size protect origin and integrity. Each archive is tied to this installation, root company ID/slug, saved company/branch hierarchy and current archive ID. Files shared within the group are included only once.
3. Download using the browser's Save dialog and select the pendrive. A web server cannot identify a USB drive or prove that the browser saved to it. Keep a second independent copy and the password. Download initiation is recorded; it does not prove successful saving.
4. Select the actual saved file and enter its archive password to verify all decrypted entries, current schema/policy and the still-paused business snapshot.
5. Removal needs the same file again, current account password, exact company name, successful verification/download and confirmation of a second copy. Records are deleted child-first inside a transaction with foreign-key enforcement enabled. Transactional storage is required for every nonempty company-owned MySQL table. Ownership checks include reviewed logical relationships where legacy migrations omit foreign keys.
6. Delete unshared business attachments and the temporary encrypted server copy. If file cleanup fails after the database commit, the company stays paused in `cleanup_pending`; use the same archive to retry cleanup or restore. Shared/account files are retained to avoid affecting another tenant or login.
7. Restore the current archive from the pendrive. Conflicting records/files are never overwritten. Files are checked and inserted business records are reconciled against the exported row digests before reopening the company. A restore failure rolls back database inserts and compensates unreferenced newly written files where possible.

New format-v5 archives retain the v3 staff-account move: non-company-admin users, their role/direct-permission assignments and their approved-device records move alongside business data. Company Admin accounts (including branch admins and legacy company_admin roles) remain live for login and restore; their user rows and profile attachments are excluded from new user snapshots. Shared role/permission definitions remain live because other users may use them; encrypted reference snapshots verify their identity and grants before removal/restore. Changed shared access definitions block restore for review rather than silently changing a user's access. Staff usernames, password hashes and 2FA configuration return, but old sessions, remember tokens, API tokens and reset links are revoked and never reactivated; staff must log in again.

Company identity, shared role/permission definitions, security/office settings, app themes, plan renewals, voucher counters and admin devices remain live and are not overwritten on restore. Reviewed nullable retained references to moved staff in the same company are saved, detached during removal and restored only if still empty; foreign-company references block the move. Staff records are inserted before dependent business rows, with foreign-key enforcement and transaction rollback on conflict. Opening-balance fields are cleared on removal and restored from the archive. Authentication tokens, sessions, password-reset tokens, global settings, queue infrastructure and other tenants are not exported or restored. The signed archive-policy configuration is unchanged. Automatic stale-request cleanup requires the separate runtime-only migration documented below.

For a group, every workspace's own opening balances are restored to its own company ID. Group business records are removed/restored in a single database transaction, and all workspace states move together. Branch controls contain only the root archive ownership link and status, never the group's private ZIP path or hash. A branch administrator cannot download/verify/remove/restore/cancel the parent's group archive. Conflicting independent branch archives block preparation before any partial freeze. Changed branch membership/ownership blocks verification/removal/restore for review; no new branch is silently added to an already downloaded ZIP. Other unrelated company workspaces remain available.

New single-company and group archives use format v5 with media_policy=cloud_paths_only, a signed reference_files map and a signed missing_optional_files map. Files on configured non-local storage (including S3/Cloudflare R2) are represented by their disk and saved path, reference count and hashed storage identity. The image bytes are not downloaded, existence-checked, hashed, uploaded or deleted during a v4 prepare/verify/remove/restore round trip. Database image paths are restored unchanged. Missing or changed cloud images cannot be recovered from the ZIP; the owner must retain the cloud account, credentials, bucket configuration and originals separately. This is a database/local-file backup with cloud references, not an independent image snapshot. Available local images and attachments are copied and checked. Missing company/branch logos, staff profile images, stock/gallery images, visiting-card images, QR logos and reviewed background-removal images are optional: they are omitted, logged and listed in the encrypted manifest and summary, without deleting database records or clearing their saved paths. Restore cannot recreate an image that was absent when the backup was made. Missing production/order documents still block preparation; a file also referenced as a required document is never treated as optional. Explicit remote profile URLs already stored in database rows remain references as before.

Existing format-v1/v2 retained-user, format-v3 staff-account and format-v4 cloud-reference ZIPs remain supported with their original embedded attachments; existing ZIPs are never silently upgraded. New removal/compensation preserves cloud originals in all environments, including for older embedded-file ZIPs. An older ZIP can still repair its missing cloud attachment from its saved bytes. Restore/cancel an existing archive, then create a fresh archive for the path-only cloud behavior. Single-company archives retain their original scope. Storage identity/path changes stop removal/restore for review; optional omissions are also checked against their current scoped references. No migration, signing-key change or change to config/company_archive.php is required, preserving existing schema/policy checks.

An archive does not erase historical backups, database logs, S3 object versions, browser caches or externally hosted files. A single raw SQL dump of the whole server is never taken. AR/external item media references that have no reviewed file ownership rule block moving data.

Cloud originals are preserved in local and production environments. New path-only archives never contact remote image storage, while local unshared attachments retain the established backup/removal/restore behavior. Old embedded-image archives retain their checksum verification and repair behavior when restoring saved bytes. A path-only restore does not verify that a remote URL remains accessible or that its image content is unchanged.

## Future updates and legacy data

`config/company_archive.php` is the explicit table/relationship/file-policy registry. Unknown tables in the selected database, unreviewed file columns, missing attachment files, mixed tenant references and unsupported ownership/transactional-storage cases stop the action. Schema inspection is limited to the selected MySQL database, not every schema visible to its DB user.

Legacy `product_background_removes` installations may lack `created_by`/`company_id`. The existing controller makes these records shared when it cannot scope by creator. The reviewed `shared_without_owner` policy retains them on the server, explicitly reports them as shared, and never guesses that they belong to DK Brothers. When an ownership column exists, its company-owned records are archived normally. Other nonempty unowned tables still fail closed. No legacy ownership/schema/data conversion is performed automatically.

New company data is included in a **newly generated** archive after its feature policy is reviewed. Old ZIP files are immutable snapshots. Old-schema archives fail closed until a reviewed compatibility converter is supplied; this release does not automatically migrate archives. Keep the installation's APP_KEY securely backed up through the existing secret-management process; rotating/losing it makes the old manifest unverifiable. The archive password cannot be recovered.

## Deployment

The feature defaults to disabled. Deploy all new files and the small hooks in `bootstrap/app.php`, `routes/web.php`, Company Profile and the existing company purge service. The purge hook prevents deletion of an account whose archive is not active. No billing, stock, casting or ledger calculation is replaced.

1. Rehearse a round trip on an isolated copy of the **actual AWS database schema and storage layout**. Fix or explicitly review ownership/file-policy gaps first. Verify required table storage is InnoDB. This release's fixture tests are not proof that a particular AWS deployment is fully covered.
2. Run only `database/migrations/2026_10_31_120000_create_company_archive_states_table.php` through the normal migration process. It creates the control table; it does not move business data. Its rollback refuses while any archive is non-active.
3. Require PHP ZIP with AES-256 encryption/decryption support, a valid application key, protected writable temporary storage, and working configured storage disks.
4. For multiple web instances, set `COMPANY_ARCHIVE_DISK` to an existing **private shared disk** (for example a configured private S3 disk) accessible by all instances. Default `local` is suitable only when the web instances actually share that storage or there is one instance. Do not use a publicly readable archive bucket.
5. Deploy request-gate code to **every** web instance and restart/drain old workers before enabling. Then set `COMPANY_ARCHIVE_ENABLED=true`, refresh configuration/route/view caches by the established deployment process, and recheck Profile.
6. Configure PHP `upload_max_filesize`, `post_max_size`, execution limits and reverse-proxy request/body timeouts for the intended archive sizes. Default expanded/upload cap is 2 GiB; server limits may be lower. Export uses private temporary plaintext staging plus an encrypted ZIP, so sufficient disk space is required. Operations are synchronous in this release; a large-company load test must fit those limits before enabling. Do not raise limits blindly for untested large data sets.

The request gate uses short transactions on a company control row, counting active standard HTTP requests; parallel tenant requests remain possible. In preparing/ready/verified/archived/cleanup-pending states, safe GET/HEAD lists, details and reports can open in view-only mode, subject to existing company/account/plan/module/role checks. Archived records remain absent until restored; opening a list does not import the ZIP. Add/edit/delete HTTP methods and legacy GET actions that create, process, finalize or change printing state stay blocked. Account login/2FA/logout and authorized archive operations retain their own access checks. During building/verifying/removing/restoring/cancelling, business navigation remains temporarily blocked.

View-only pages disable mutating controls (the notice banner is commented out at the owner's request), including AJAX-loaded row buttons. The backend rejects forged saves independently of JavaScript. Read handlers and streamed report callbacks run in a rollback-only transaction on the existing default database connection, preventing incidental defaults/notification updates from persisting. Known automatic category/worker/permission synchronization is skipped in read-only requests so cached permissions cannot incorporate temporary defaults. Read leases prevent removal/restore transitions while a view/export is running, and are released after rendering/output. Existing JSON payload formats are preserved; X-Company-Archive-Read-Only: 1 marks responses. This is not a filesystem/external-service sandbox: future GET handlers must still be reviewed for external effects or secondary DB connections. Mutating legacy GET handlers are deliberately not treated as navigation.

Other companies remain available. Normal active requests acquire/release a lease only when the feature is enabled. Active/restored workspaces retain ordinary write behavior. Disabling the feature flag does **not** enable writes in an already paused/archived company.

Database/sync queues must drain for the selected company, including the stock-gallery queue connection. Preparation/removal/restore reject its queued/reserved image jobs and any unclassified job. Known other-company image jobs, reviewed stale no-op media jobs and account-only CompanyLoginMail jobs do not block it. Queue inspection reads JSON/serialized metadata without unserializing or executing commands. External queue connections fail closed. No queue job is sent, processed or deleted by these checks. There is no blanket queue purge, global cache flush or worker shutdown affecting other tenants. Command-line scripts/direct database writers are outside HTTP request accounting and must honor the archive gate or be stopped for the company during the operation. Direct file access/caches and existing backup retention are outside the company's HTTP business-route gate.

If a process or server dies in `building`, `verifying`, `removing`, `restoring` or `cancelling`, the company stays paused. Do not reset counters/status blindly: inspect DB transaction outcome, current archive hash and file inventory, verify no operation/request is still running, and repair the state under an operator-controlled recovery procedure. Failed cleanup is explicitly retryable; an arbitrary killed process is not automatically declared successful. Keep APP_KEY, encrypted archive copies and recovery passwords secure. There is no automatic archive expiry that could destroy the only recovery file.

## Validation

### Handled prepare failures and normal company access

Relationship/ownership checks now run before company pause and are repeated after the request drain. A handled build failure before `saving_zip` may resume the group automatically only when the locked group still matches the failed request UUID, the recorded error is `BUILD_FAILED` at a known pre-save stage, current hierarchy matches, every counter is zero, the tracked-request registry is empty for the group, and no saved archive ID/path/hash/download/verification metadata exists. Only archive control status and failure diagnostics change; business rows and payment links do not.

For legacy `preparing` rows with that same completed-failure evidence, the business-route middleware applies the guarded recovery before access checks. This prevents a failed backup from repeatedly redirecting Jobwork edit to Profile. Root failure diagnostics move to `last_prepare_failure`; branch ownership/pause markers are released together. Unhandled/fatal operations, `building` operations from other requests, saving/saved ZIPs, missing or mixed group controls, nonzero counters and active tracked leases stay protected for review. Successful `ready`/`verified` archives and removal/restore states remain paused as before. This upgrade requires no migration.

### Automatic cleanup of terminated HTTP requests

Install the runtime-only request registry with this targeted migration (do not run unrelated pending migrations):

```sh
php artisan migrate --path=database/migrations/2026_11_21_230000_create_company_archive_request_leases_table.php --force
```

Deploy `CompanyArchiveRequestLeases.php`, `CompanyArchiveGate.php`, `CompanyArchiveScope.php`, `CompanyArchiveInventory.php`, `CompanyArchiveLog.php`, and `CompanyArchiveApiController.php` together. Existing `CompanyArchiveAccess.php` must include the previously installed `protectRequests` shutdown guard. With the registry absent, the existing fail-closed counter and shutdown cleanup remain in effect.

New admitted requests receive a UUID, a registry row, and an exclusively held OS lock under `storage/app/private/company-archive-request-leases`. Admission and release update the registry and counter in the same database transaction. At the next archive transition/retry, only a lease from this server/storage identity with the original file identity and proof, whose exclusive lock is now obtainable, can be removed. A long-running live request remains counted regardless of its age. This relies on local filesystem [`flock`](https://www.php.net/manual/en/function.flock.php), not a timeout or heartbeat. Unix threaded PHP SAPIs use the existing fail-closed mode instead.

Missing/replaced lock files, unavailable storage, a different server/node identity, a mismatched registry/counter, or old counters without individual lease records are never assumed dead. Preserve this private directory across restarts/deployments and do not copy it between installations, delete it, or put it in ephemeral/public storage. Another server's abandoned requests require that server's recovery check; their counts are not reset from a different node. Database-imported legacy counters still need one reviewed recovery when their original request identity is unavailable.

Only runtime control rows and private proof files are affected. Business records, cloud images, archive ZIPs, and signed archive policy/schema fingerprints remain unchanged. The registry is not exported to a pendrive. Rollback of its migration is blocked while any registry records remain. `stale_request_cleared` is logged only after the surrounding archive transition commits; `untracked_requests_retained` identifies counters that cannot safely be auto-cleared.

`tests/Feature/CompanyArchiveTest.php` requires SQLite in-memory and refuses any configured non-test database before fixture DDL. It covers an encrypted binary-safe round trip, original/other-company balances, inherited child records, shared/legacy images, wrong passwords/company/modified ZIPs, future tables/attachment columns, schema changes, missing files, conflicts, rollback, queue/request drain, scope/password authorization, form rendering, disabled-feature gating, interrupted cleanup and purge protection.

Use explicit DB_CONNECTION=sqlite, DB_DATABASE=:memory:, CACHE_STORE=array, SESSION_DRIVER=array and QUEUE_CONNECTION=sync. No production migration/data removal is needed to run these tests.
